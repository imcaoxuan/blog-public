在一台内存较小的 Debian 服务器上，我原先使用 CrowdSec 分析 SSH 和 Web 日志，再通过 Firewall Bouncer 将封禁决策同步到 nftables。

这套方案能够根据攻击行为动态封禁 IP，但对于只有数百 MiB 内存、运行多个个人服务的服务器，资源开销需要重新权衡。最终我采用了以下组合：

  • 网站：Caddy + GeoIP 地区白名单 + 手动 IP 白名单。
  • SSH：Fail2ban 读取 systemd journal，通过 nftables 封禁异常来源。

本文记录完整改造方法，以及部署过程中遇到的日志来源和启动时序问题。所有域名、地址和主机标识均已替换为示例。命令按 root 用户执行。

一、先明确防护能力的变化#

项目原方案新方案
Web 访问控制CrowdSec 分析日志并生成封禁决策Caddy 按来源地区或 IP 放行
SSH 异常登录CrowdSec SSH 场景Fail2ban SSH jail
Web 行为检测取决于安装的 Collection 和 Scenario本文没有保留
社区威胁情报可使用 CrowdSec 社区名单本文没有接入
Web 拒绝位置Firewall Bouncer 的防火墙规则Caddy HTTP 请求处理阶段

地区白名单不能等价替代行为检测。允许地区内的恶意请求仍可能到达应用，Caddy 的 GeoIP 规则也不会覆盖没有经过它的其他公网端口。

二、查看内存时，同时检查 RSS 和 Swap#

首先查看整体情况：

free -h

systemctl show crowdsec crowdsec-firewall-bouncer \
    -p Id -p MemoryCurrent

ps -eo pid,comm,rss,args --sort=-rss | head -n 15

单看 RSS 可能低估进程占用，因为部分匿名内存已经被换出。可以按 RSS 与 Swap 的合计排序：

for status_file in /proc/[0-9]*/status; do
    awk '
        /^Name:/   { name=$2 }
        /^VmRSS:/  { rss=$2 }
        /^VmSwap:/ { swap=$2 }
        END {
            if (rss+swap > 0)
                printf "%12d %12d %12d %s\n", rss+swap, rss, swap, name
        }
    ' "$status_file" 2>/dev/null
done | sort -nr | head -n 5

四列依次是：合计 KiB、RSS KiB、Swap KiB、进程名。这是进程排名；同一个服务如果有多个进程，需要进一步归并。

在这次排查中，CrowdSec 的 RSS 约为 42 MiB，VmSwap 约为 225 MiB，粗略合计约 267 MiB。这说明它确实是值得精简的组件，但不能把 267 MiB 全部当成物理内存。

还要区分“已经使用 Swap”和“正在频繁换页”：

vmstat 1 10

观察第一行之后的采样数据，si、so 分别表示每秒换入、换出量。Swap 使用量较大，本身不代表当前正在发生持续换页。

对于其他高占用进程，可以用 PID 定位服务：

systemctl status 实际PID --no-pager --full

确认用途后再选择停用：

systemctl disable --now 实际服务名.service

三、备份与停用 CrowdSec#

建议在开始前保存配置；有条件时先完成新方案验证，再停用旧方案，以缩短防护切换间隔。

以下备份目录按首次迁移使用。重复操作时换一个目录，避免覆盖初始状态。

install -d -m 0700 /root/security-migration-backup

cp -a /etc/crowdsec /root/security-migration-backup/
cp -a /etc/caddy /root/security-migration-backup/
cp -a /usr/bin/caddy /root/security-migration-backup/caddy.original

nft list ruleset > /root/security-migration-backup/nftables.before.nft

systemctl list-unit-files --no-pager 'crowdsec*' \
    > /root/security-migration-backup/crowdsec-units.before.txt

这里假设原 Caddy 二进制位于 /usr/bin/caddy。如果实际不同，应先检查服务定义：

systemctl cat caddy

3.1 停用定时任务和常驻服务#

先检查 CrowdSec 相关单元：

systemctl list-unit-files --no-pager 'crowdsec*'

下面的循环使用 Bash，停用发现的 CrowdSec timer：

while read -r crowdsec_timer _; do
    if [ -n "$crowdsec_timer" ]; then
        systemctl disable --now "$crowdsec_timer"
    fi
done < <(
    systemctl list-unit-files \
        --type=timer --no-legend --no-pager 'crowdsec*'
)

先停 Bouncer，再停引擎，并屏蔽两个单元以防被再次启动：

systemctl disable --now crowdsec-firewall-bouncer.service
systemctl disable --now crowdsec.service

systemctl mask crowdsec.service crowdsec-firewall-bouncer.service

检查结果：

systemctl is-active crowdsec crowdsec-firewall-bouncer
systemctl is-enabled crowdsec crowdsec-firewall-bouncer

预期分别为 inactive 和 masked。SSH、Caddy、Nginx 的 Collection 都由 CrowdSec 引擎执行，无需逐个停用。

3.2 检查防火墙残留#

nft list tables

默认配置通常使用 table ip crowdsec 和 table ip6 crowdsec6。如果停用后仍存在，先对照 /etc/crowdsec/bouncers/ 下的实际配置，确认它们是 Bouncer 专用表，再删除：

nft delete table ip crowdsec
nft delete table ip6 crowdsec6

只执行实际存在、确认属于 CrowdSec 的表对应的命令。不要执行 nft flush ruleset，也不要停用 nftables 服务。

如果之前曾手工将 CrowdSec 规则写入 /etc/nftables.conf 或其引用文件，还要移除对应持久化定义。

暂时保留软件包和配置，便于回退；停用服务已经能够释放其运行资源。

四、为 Caddy 添加 GeoIP 模块#

本文使用第三方模块 porech/caddy-maxmind-geolocation。它通过 MaxMind 兼容的本地 MMDB 数据库匹配客户端来源。

4.1 记录现有版本和插件#

/usr/bin/caddy version
/usr/bin/caddy list-modules --packages --versions
systemctl cat caddy

现有的 DNS、限流等插件需要一并保留。不要使用一个只包含 GeoIP 模块的新二进制直接替换原文件。

4.2 在副本上添加模块#

对于小内存服务器，可以使用 Caddy 的在线构建下载功能，避免本机运行 Go 编译：

install -d -m 0755 /usr/local/lib/caddy

install -m 0755 \
    /usr/bin/caddy \
    /usr/local/lib/caddy/caddy

/usr/local/lib/caddy/caddy add-package \
    github.com/porech/caddy-maxmind-geolocation

add-package 会更新到最新 Caddy，并重新包含现有已注册插件及新增插件，不保证保留原核心版本。 此时修改的是副本，运行中的服务和原 /usr/bin/caddy 尚未改变。

如果必须固定核心和插件版本，应在另一台有足够资源的机器上用 xcaddy 指定版本构建，并上传与目标系统及架构匹配的二进制。

检查新版本、插件清单以及现有配置兼容性：

/usr/local/lib/caddy/caddy version
/usr/local/lib/caddy/caddy list-modules --packages --versions

/usr/local/lib/caddy/caddy validate \
    --config /etc/caddy/Caddyfile \
    --adapter caddyfile

如果现有插件无法重建，或者原配置验证失败，应先解决兼容性问题，再切换服务。

4.3 安装 Country 数据库#

从 MaxMind 官方网站获取 GeoLite2 Country 的 MMDB 数据库。下载解压后，假设文件放在 /tmp/GeoLite2-Country.mmdb：

install -d -o root -g caddy -m 0750 /var/lib/caddy/geoip

install -o root -g caddy -m 0640 \
    /tmp/GeoLite2-Country.mmdb \
    /var/lib/caddy/geoip/GeoLite2-Country.mmdb

runuser -u caddy -- test -r \
    /var/lib/caddy/geoip/GeoLite2-Country.mmdb

最后一条命令成功退出，表示 Caddy 用户可以读取数据库。这里假设服务运行用户和组均为 caddy，应与实际 unit 定义一致。

只判断国家或地区时，Country 数据库即可。Xray 的 geoip.dat 不是这个插件可直接使用的 MMDB 文件。

五、集中配置地区白名单与手动 IP 白名单#

5.1 定义公共 snippet#

这个模块没有放进 Caddyfile 全局 {} 后自动作用于所有站点的选项。可以通过 snippet 集中维护，再由各站点引用。

在 /etc/caddy/Caddyfile 中，放在已有全局选项块之后、站点定义之外：

(geo_whitelist) {
    @geo_denied {
        # 手动 IP 白名单：替换为实际需要放行的 IP 或 CIDR
        not client_ip 203.0.113.10 198.51.100.0/24 2001:db8::10

        # 地区白名单
        not {
            maxmind_geolocation {
                db_path /var/lib/caddy/geoip/GeoLite2-Country.mmdb
                allow_countries CN HK JP
            }
        }
    }
}

上面的地址都是文档示例地址。单个 IPv4、IPv6 和 CIDR 网段均可使用；如果不需要手动白名单，删除 not client_ip ... 这一行。

这两个 not 表示：既不在手动 IP 白名单，也不属于允许地区，才匹配拒绝规则。 不要把正向的 client_ip 和 GeoIP 匹配直接并列，否则会变成必须同时满足的条件。

来源处理结果
手动 IP 白名单中的地址通过 GeoIP 访问控制
CN、HK、JP 的其他地址通过 GeoIP 访问控制
其他地址或无法识别地区的地址返回 403

白名单只豁免地区限制，原有 mTLS、应用登录等认证机制仍然有效。

5.2 在各站点引用，并保证先检查再处理业务#

app.example.com {
    import geo_whitelist

    # 原有 tls、log 等站点级配置保留在这里

    route {
        respond @geo_denied "Forbidden" 403

        handle {
            # 原有请求处理逻辑放在这里
            reverse_proxy 127.0.0.1:8080
        }
    }
}

files.example.com {
    import geo_whitelist

    route {
        respond @geo_denied "Forbidden" 403

        handle {
            reverse_proxy 127.0.0.1:9090
        }
    }
}

外层 route 按书写顺序执行，确保先检查 GeoIP；内层 handle 保留原有业务指令的正常排序。原站点其他 handle、handle_path、reverse_proxy 或 file_server 等业务处理，也应放入受保护的内层，避免绕过检查。

只在站点第一行写一个 respond，并不能保证它最先执行，因为 Caddy 默认会重新排序指令。

每个需要保护的站点都必须引用并使用这套检查；snippet 不是自动覆盖所有站点的全局防火墙。

5.3 真实客户端 IP#

本例适用于公网客户端直接连接 Caddy。若前面还有 CDN 或反向代理，需要配置准确的 trusted_proxies，使 client_ip 和 GeoIP 模块使用真实客户端地址。

仅在头部中传入 X-Forwarded-For 不等于可信，不能无条件信任任意来源。普通 TCP 中转若没有保留真实来源的机制，Caddy 看到的可能只是中转服务器 IP。

六、让 systemd 使用独立的 Caddy 二进制#

使用独立路径和 drop-in，可以避免后续 APT 更新 /usr/bin/caddy 时覆盖当前使用的自定义二进制。自定义二进制之后也需要自行维护更新。

install -d -m 0755 /etc/systemd/system/caddy.service.d

vim /etc/systemd/system/caddy.service.d/90-geoip-binary.conf

写入：

[Service]
ExecStart=
ExecStart=/usr/local/lib/caddy/caddy run --environ --config /etc/caddy/Caddyfile

ExecReload=
ExecReload=/usr/local/lib/caddy/caddy reload --config /etc/caddy/Caddyfile --force

如果原服务使用不同参数、配置路径或适配器，需要按实际启动命令调整。

验证后切换：

/usr/local/lib/caddy/caddy validate \
    --config /etc/caddy/Caddyfile \
    --adapter caddyfile

验证成功后执行：

systemctl daemon-reload
systemctl restart caddy

systemctl status caddy --no-pager
journalctl -u caddy -n 50 --no-pager

首次切换二进制需要 restart，会短暂中断连接。之后只修改配置时使用：

systemctl reload caddy

使用不同地区的出口测试，或使用不在手动白名单中的测试服务器：

curl -I https://app.example.com/

允许来源应进入后端处理，其他来源应返回 403。本机及内网地址通常没有国家归属，如需本机监控，应明确加入必要的 IP 白名单。

七、用 Fail2ban 保护 SSH#

本文实际验证的 Fail2ban 版本为 Debian 12 仓库提供的 1.0.2。

7.1 安装与检查#

apt update
apt install fail2ban python3-systemd nftables

fail2ban-client -V

/usr/sbin/sshd -T | grep '^port '
ss -lntp | grep sshd
journalctl -u ssh.service -n 20 --no-pager

以下配置假设 SSH 端口为 22；实际不是 22 时必须修改。

7.2 创建 SSH jail#

vim /etc/fail2ban/jail.d/90-sshd.local

写入：

[sshd]
enabled = true

backend = systemd
journalmatch = _SYSTEMD_UNIT=ssh.service + _COMM=sshd
filter = sshd[mode=normal]

port = 22
protocol = tcp
banaction = nftables[type=multiport]

usedns = no
ignoreip = 127.0.0.1/8 ::1

findtime = 10m
maxretry = 5
bantime = 1h

同一来源在 10 分钟内累计匹配 5 条失败事件，就会被封禁 SSH 端口 1 小时。匹配事件数不一定等于连接数。

journalmatch 中的 + 表示两组条件之间的 OR。使用 systemd 后端时，不要再设置文件型 logpath。已有固定可信管理出口时，可以按需加入 ignoreip。

.local 文件用于覆盖配置，避免修改软件包自带的 .conf 文件。

7.3 验证并启动#

fail2ban-client -t

检查通过后：

systemctl enable fail2ban
systemctl restart fail2ban

稍等几秒，再检查：

fail2ban-client ping
fail2ban-client status
fail2ban-client status sshd

预期 ping 返回 pong，Jail 列表只包含需要启用的项目。若存在旧配置启用的其他 jail，应在相应 .local 文件中明确关闭。

保持现有 SSH 会话，再开一个终端验证正常密钥登录。

八、两个常见启动问题#

8.1 找不到 SSH 日志文件#

ERROR Failed during configuration: Have not found any log file for sshd jail

这通常是当前 jail 在查找文件日志，而系统实际使用 journal。先用 journalctl -u ssh.service 确认日志存在，再配置 backend = systemd、安装 python3-systemd 并重启。

8.2 客户端找不到 socket#

ERROR Failed to access socket path: /var/run/fail2ban/fail2ban.sock.
Is fail2ban running?

这是客户端连接失败，不能仅凭这一行就认定服务启动失败。本次部署中，客户端在启动后的同一秒发起检查，而服务下一秒才报告 Server ready，稍后检查即正常。

排查命令：

fail2ban-client -t
systemctl status fail2ban --no-pager --full
journalctl -u fail2ban -b -n 80 --no-pager
tail -n 80 /var/log/fail2ban.log

无需手动创建 socket，应由服务进程创建。

如果看到：

WARNING 'allowipv6' not defined in 'Definition'. Using default one: 'auto'

这是采用默认值 auto 的警告，本次部署没有因此启动失败。

九、验证 Fail2ban 的实际拦截效果#

9.1 先验证 IPv4、IPv6 规则生成#

用文档保留地址测试规则同步：

fail2ban-client set sshd banip 203.0.113.10
fail2ban-client set sshd banip 2001:db8::10

nft list table inet f2b-table

检查集合中是否出现地址，关联规则是否匹配实际 SSH 端口。默认 nftables 动作可能在首次封禁时才创建规则，所以尚无封禁时看不到表，不一定是故障。

完成后解除：

fail2ban-client set sshd unbanip 203.0.113.10
fail2ban-client set sshd unbanip 2001:db8::10

这一测试验证执行链路，不能证明日志检测条件和真实网络阻断都已验证。封禁记录可能在服务重启后恢复，测试结束应显式解除。

9.2 从另一台受控服务器验证连接#

在目标服务器上封禁另一台受控服务器的真实公网 IP：

fail2ban-client set sshd banip 测试服务器实际公网IPv4

然后在被封禁的服务器上，新建连接：

nc -4 -vz -w 5 目标服务器实际公网IPv4 22

也可以观察 SSH 握手：

ssh -4 -vvv \
    -o ConnectTimeout=5 \
    -o ConnectionAttempts=1 \
    -p 22 testuser@目标服务器实际公网IPv4

示例中的中文占位内容和端口均需替换。默认 nftables 动作为 reject，连接可能立即报拒绝；如果改成 drop，通常表现为超时。进入 SSH 主机密钥提示或认证阶段，说明这个新连接没有被该封禁阻止。

需要时，在目标服务器抓包确认请求是否到达：

tcpdump -ni any -nn \
    'host 测试服务器实际公网IPv4 and tcp port 22'

tcpdump 能看到 SYN，不代表防火墙已经放行。

解除后，从测试服务器重复连接：

fail2ban-client set sshd unbanip 测试服务器实际公网IPv4

封禁时连接失败，解除后连接成功，才是直观的对照结果。使用明确的 IPv4 地址与 -4，避免连接实际走 IPv6，而封禁的只是 IPv4。不要使用当前唯一的管理来源做封禁测试。

十、插件开销与数据库维护#

根据检查时的项目源码，这个 GeoIP 插件在首次匹配时打开数据库 Reader，后续复用；执行匹配器时进行本地查询，没有远程 GeoIP API 请求，也没有额外的 IP 查询结果缓存。

它使用的 maxminddb-golang 在 Linux 上支持 mmap。映射文件仍会消耗物理内存，但数据库文件大小不能直接当作新增 Go 堆内存。snippet 是配置复用，并不保证各站点共享同一个插件实例；同一文件的映射页面可由操作系统共享。

对于个人服务，预计额外开销较小，但这里没有对本机测出确定的 QPS、查询延迟或插件净增内存。WebSocket 等长连接建立后的数据帧不会逐包重新执行这条 GeoIP 检查。

只使用 Country 数据库，并在日常运行时关闭不需要的全局 debug，可以减少不必要的数据量和逐请求调试日志。

查看整个 Caddy 的实际内存：

systemctl show caddy -p MemoryCurrent

caddy_pid=$(systemctl show caddy -p MainPID --value)

awk '/^(Rss|Pss|Swap|SwapPss):/' \
    "/proc/$caddy_pid/smaps_rollup"

数据库需要持续维护。更新时应先写入同一目录下的新文件，再通过重命名替换，避免直接截断正在被 mmap 使用的原文件：

install -o root -g caddy -m 0640 \
    /tmp/GeoLite2-Country.mmdb \
    /var/lib/caddy/geoip/GeoLite2-Country.mmdb.new

mv -f \
    /var/lib/caddy/geoip/GeoLite2-Country.mmdb.new \
    /var/lib/caddy/geoip/GeoLite2-Country.mmdb

systemctl reload caddy

这里的 reload 依赖前面 drop-in 中的 --force，确保配置文本未变化时也重新加载。插件本身不会自动下载数据库。

十一、验收与回退#

验收时确认：

  • CrowdSec 与 Firewall Bouncer 已停止，相关 timer 已停用。
  • Caddy 实际运行的新二进制包含 GeoIP 和原有插件。
  • 允许地区与手动 IP 白名单能够通过；其他来源获得 403。
  • Fail2ban 的 SSH jail 已开始处理新 journal 日志。
  • IPv4、IPv6 规则生成，以及真实连接的封禁／解封对照测试通过。
  • 正常 SSH 密钥登录和现有应用访问没有受到意外影响。

查看服务状态和总体内存：

systemctl is-active caddy fail2ban
systemctl is-active crowdsec crowdsec-firewall-bouncer

free -h

需要回退到原方案时：

systemctl disable --now fail2ban

cp -a /root/security-migration-backup/caddy/. /etc/caddy/

rm /etc/systemd/system/caddy.service.d/90-geoip-binary.conf

systemctl daemon-reload
systemctl restart caddy

systemctl unmask crowdsec.service crowdsec-firewall-bouncer.service
systemctl enable --now crowdsec.service
systemctl enable --now crowdsec-firewall-bouncer.service

此流程保留了原 /usr/bin/caddy 和 CrowdSec 配置。若原先还启用了 timer，按照备份的单元状态恢复对应项目。Bouncer 启动后会重新同步决策，无需盲目将整个旧防火墙快照覆盖回去。
