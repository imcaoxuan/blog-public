sing-box 低流量高 CPU 排查：process_name 引发的进程查询开销

使用 Go pprof 定位 sing-box 高 CPU：约 84% 的 CPU 采样落在进程归属查询路径。

结论与验证状态#

本次排查定位到：sing-box 的主要 CPU 开销来自连接所属进程查询，尤其是构建进程路径信息的 buildProcessPaths。故障出现前刚新增了 process_name 匹配规则，该变更与热点高度吻合，是首要触发因素。

已验证的是性能热点；尚未收到移除规则后的对照复测结果。 因此不能把“已移除并恢复正常”写成既成事实，也不能直接归因于某个已确认的版本 Bug。

本文已去除个人主机名、账户名，将原规则中的程序名替换为 example-cli。

环境与现象#

  • 设备：N1，Linux ARM64。
  • sing-box：1.14.4。
  • Go 构建环境：go1.26.10 linux/arm64，CGO enabled。
  • Revision：c005f35300ce76427dc285481ec5695f5b179cd2。
  • 现象：外部流量低、日志平静，但 CPU 持续很高。
  • perf 未安装；最终采用 sing-box 内置 pprof，在 Mac 上分析采样。

最初 top 输出：

PID    COMMAND   VIRT     RES     SHR    %CPU   %MEM  TIME+
20776  sing-box  1484040  130060  41288  355.4   7.1  139:35.45

在通常的 top CPU 计数模式下，355.4% 表示约占用 3.55 个核心。RES 约 127 MiB；VIRT 约 1.42 GiB 并不等于实际物理内存占用。TIME+ 是累计 CPU 时间。

初始猜测包括忙循环、GC 压力和内部流量回环；这些仅是排查方向，不能当作诊断结果。

采集 CPU profile#

1. 先确认版本与启动参数#

以下命令在目标 Linux 主机执行：

sing-box version
systemctl show sing-box -p ExecStart --no-pager
command -v perf

command -v perf 没有输出，随后 perf 命令报 command not found，因此没有取得 perf 采样。root 用户不需要再加 sudo。

2. 启用本机 pprof 接口#

以下示例假定服务使用 /etc/sing-box/config.json。如果实际使用 -C 配置目录或其他参数，check 应采用相同参数，不能只检查其中一个文件。

备份配置：

cp -a /etc/sing-box/config.json \
  "/etc/sing-box/config.json.bak.$(date +%Y%m%d-%H%M%S)"

将下面的 debug 字段合并到已有 experimental 中，保留原配置；这不是完整运行配置：

{
  "experimental": {
    "debug": {
      "listen": "127.0.0.1:6060"
    }
  }
}

调试接口仅监听 loopback，不应直接暴露到公网。检查成功后重启：

sing-box check -c /etc/sing-box/config.json &&
systemctl restart sing-box

重启会短暂中断代理连接并清除当时运行状态。如果异常消失，应等高 CPU 复现后再采样。此次实际取得了 profile，证明该调试路径在此构建中可用；排查时未能取得对应 Revision 的完整源码，不能将 testing 分支源码视作该构建的精确实现。

3. 在异常期间采样#

curl --noproxy '*' -fsS http://127.0.0.1:6060/debug/pprof/

curl --noproxy '*' -fS --max-time 45 \
  -o /tmp/sing-box-cpu.pprof \
  'http://127.0.0.1:6060/debug/pprof/profile?seconds=30'

curl --noproxy '*' -fsS --max-time 15 \
  -o /tmp/sing-box-goroutines.txt \
  'http://127.0.0.1:6060/debug/pprof/goroutine?debug=2'

–noproxy ‘*’ 防止环境变量中的代理干扰本地请求。goroutine 文件是补充诊断材料，本次结论来自 CPU profile，不依赖未提供的 goroutine 内容。

4. 在安装 Go 的电脑分析#

将 profile 复制到 Mac 或其他安装 Go 的电脑，不必在 N1 上安装 Go：

go tool pprof -top /tmp/sing-box-cpu.pprof
go tool pprof -top -cum /tmp/sing-box-cpu.pprof

如何读懂本次证据#

采样摘要：

Duration: 30s
Total samples = 66.94s (223.12%)

这 30 秒的平均 CPU 使用约为 223%，与此前 top 的 355.4% 属于不同时间窗口，不矛盾。

函数或路径累计采样时间累计占比
direct Inbound.NewPacketConnectionEx58.41s87.26%
Router.searchProcessInfo56.54s84.46%
process.FindProcessInfo56.33s84.15%
process.buildProcessPaths54.37s81.22%
syscall.Readlink30.39s45.40%
os.ReadDir13.83s20.66%
runtime.gcBgMarkWorker3.57s5.33%

主要调用路径可概括为：

direct 入站 UDP 连接处理
→ 路由匹配
→ searchProcessInfo / FindProcessInfo
→ findProcessPath / buildProcessPaths
→ ReadDir、Readlink 等系统调用

flat 表示函数自身的采样时间，cum 包含其子调用。上述父子路径彼此重叠，不能把百分比相加。Syscall6 的 flat 占比高达 64.03%，但仅看它不能定位业务原因；结合 cum 才能追溯到进程查询。

本次主要开销不是 GC，也没有证据把主要开销归因于加密或大吞吐转发。

注意：protocol/direct.(*Inbound) 指 direct 入站，不代表流量选择了 direct 出站。若该入站用于接收 DNS，应继续检查该入口；单凭函数名不能确定流量就是 DNS，也不能证明存在回环。

触发配置与 find_process 的误区#

故障前新增了类似匹配条件：

{
  "process_name": ["example-cli"]
}

这只是原配置中的匹配片段，不是完整规则示例。

为了判断连接是否来自该程序，sing-box 必须查询进程归属。即使最终不匹配，也可能已经付出了查询成本。这解释了为什么流量字节数不大，CPU 仍可能很高；采样本身不能证明是查询次数、单次扫描成本还是缓存行为中的哪一项突然变化。

find_process: false 不是强制禁止进程查询的总开关。 官方文档将它定义为：没有 process_name、process_path、package_name、user、user_id 等规则时，为日志额外启用进程查询。规则本身需要进程信息时，仅关闭该选项不足以消除查询。

此外：

  • 进程匹配针对代理所在主机的本地进程，不能识别其他设备上的应用进程。
  • Python CLI 的命令名不一定等于系统报告的进程名，不能假定 example-cli 一定匹配；应核对实际进程信息。
  • 不能仅凭此案例断言所有 process_name 规则都会造成高 CPU。

最小修复与验收#

先查找相关配置：

grep -RInE \
  '"(find_process|process_name|process_path|process_path_regex|package_name|user|user_id)"' \
  /etc/sing-box --include='*.json' --include='*.jsonc'

该搜索只覆盖上述文本配置，不会展开二进制规则集；结果也可能包含未加载的文件，应结合启动参数判断。

推荐步骤：

  1. 备份当前配置。
  2. 移除刚新增的整条进程匹配规则，恢复此前的规则状态。不要只删除匹配字段而保留 action，否则可能变成无条件规则。
  3. 如无进程匹配需求，将额外启用的 find_process 设为 false。
  4. 使用实际加载参数执行 check，成功后重启。
  5. 在相同客户端活动和流量条件下观察 CPU，并重新采集 30 秒 profile。

验收标准：

  • CPU 明显下降，并在观察期间保持稳定。
  • 新 profile 中进程查询路径不再占据主要 CPU。
  • 原有 DNS 和代理分流行为符合预期。

重启本身可能暂时缓解异常，因此不能仅凭刚重启后的瞬时低 CPU 判定根因已完全验证。若热点仍存在，应检查其他已加载的进程/用户规则及 direct UDP 入站请求来源，而不是盲目修改 TUN、GC 或 QUIC 参数。

如修改影响业务，恢复备份并检查后重启；恢复进程规则也可能重新引入高 CPU。排查完成后移除新增 debug 配置并重启，关闭调试端口。
