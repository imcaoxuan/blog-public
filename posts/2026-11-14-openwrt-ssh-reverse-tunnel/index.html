OpenWrt 使用 SSH 反向隧道向云服务器提供本地服务

使用 SSH -R 转发本地 3143 服务，并通过 procd 实现开机启动与断线重连。

目标与环境#

本地 OpenWrt 已有服务监听 127.0.0.1:3143，希望云服务器通过自身的 127.0.0.1:3143 访问这个服务。由 OpenWrt 主动建立 SSH 连接，适用于本地处于 NAT 后方的场景。

环境为 OpenWrt 23.05.2 x86_64，客户端使用 OpenSSH，云服务器运行 sshd。文中域名、用户和密钥路径均为示例，需要替换为实际值。

本次已确认反向隧道可用。后续观察到云服务器监听 :::3143，最终决定保留现有服务端设置。procd 配置是常驻运行方案，其重启和断网恢复仍应按本文步骤自行验收。

安装与前台验证#

在 OpenWrt 上执行。

opkg update
opkg install openssh-client
/usr/bin/ssh -V

准备能无人值守登录云服务器的 SSH 密钥。示例私钥为 /etc/ssh/vps-3143_ed25519，对应公钥需安装到云服务器用户的 authorized_keys。首次连接时核对服务器 host key。已有可用密钥和 SSH Host 配置时，沿用实际配置即可。

/usr/bin/ssh -NT \
    -i /etc/ssh/vps-3143_ed25519 \
    -o ExitOnForwardFailure=yes \
    -R 127.0.0.1:3143:127.0.0.1:3143 \
    tunnel@example.com

-R 的前一组地址是云服务器请求监听的地址，后一组地址是从 OpenWrt 访问的目标。此命令不会在 OpenWrt 上新建 3143 监听，本地已有服务应继续运行。云服务器上的对应监听端口需要空闲。

如果实际服务在其他 LAN 主机上，将右侧目标改为该主机地址，例如 -R 127.0.0.1:3143:192.168.10.20:3143。

在云服务器上验证。以下仅适用于 HTTP 服务，HTTPS 服务应使用实际域名、协议和证书配置。

curl -v http://127.0.0.1:3143/

procd 常驻配置#

在 OpenWrt 上创建 /etc/init.d/vps-tunnel-3143。

#!/bin/sh /etc/rc.common

START=95
USE_PROCD=1

start_service() {
    procd_open_instance
    procd_set_param command /usr/bin/ssh -NT \
        -i /etc/ssh/vps-3143_ed25519 \
        -o BatchMode=yes \
        -o ExitOnForwardFailure=yes \
        -o ConnectTimeout=10 \
        -o ServerAliveInterval=15 \
        -o ServerAliveCountMax=3 \
        -R 127.0.0.1:3143:127.0.0.1:3143 \
        tunnel@example.com
    procd_set_param respawn 3600 10 0
    procd_set_param stdout 1
    procd_set_param stderr 1
    procd_close_instance
}

保持 SSH 前台运行，由 procd 管理进程。BatchMode=yes 禁止密码等交互提示，需确保密钥可供服务进程直接使用。ConnectTimeout=10 限制连接建立等待时间。连续三次 15 秒的 keepalive 探测未获响应时，SSH 约 45 秒后退出。respawn 3600 10 0 设置异常退出计数窗口为 3600 秒、重启等待为 10 秒、重试次数不设上限。

ExitOnForwardFailure=yes 让远程监听建立失败时退出。目标服务暂时不可达时，已经建立的 SSH 隧道仍可能正常运行，因此需要另外请求服务验证。

先结束手动测试隧道，避免占用云服务器端口，然后启用服务。

chmod +x /etc/init.d/vps-tunnel-3143
/etc/init.d/vps-tunnel-3143 enable
/etc/init.d/vps-tunnel-3143 restart

验证与维护#

在 OpenWrt 上查看进程状态和日志。

ubus call service list '{"name":"vps-tunnel-3143"}'
logread -e vps-tunnel-3143

在云服务器上检查监听并请求应用。

sudo ss -lntp 'sport = :3143'
curl -v http://127.0.0.1:3143/

验收包括应用请求成功、OpenWrt 重启后自动恢复，以及短暂断网恢复后隧道能重新连接。重连会中断已有 TCP 连接，应用需要重新建立连接。

修改脚本后执行 /etc/init.d/vps-tunnel-3143 restart。停止并取消开机启动可执行以下命令。

/etc/init.d/vps-tunnel-3143 stop
/etc/init.d/vps-tunnel-3143 disable

排查经过#

报错 Could not request local forwarding#

曾出现以下输出。

bind [127.0.0.1]:3143: Address in use
channel_setup_fwd_listener_tcpip: cannot listen to port: 3143
Could not request local forwarding.

这说明 SSH 正在请求本地转发。检查实际命令是否还包含 -L，以及 SSH 配置是否包含 LocalForward。本地 3143 已被目标服务占用属于预期状态。

-F /dev/null 可临时排除用户和系统 SSH 配置的影响，但同时会跳过 Host 别名、端口、私钥和 ProxyJump 等配置。正常运行无需默认加入该参数。本次未取得完整旧命令和配置，因此未确认额外本地转发究竟来自哪里。

云服务器监听 :::3143#

实际观察到 sshd 监听 :::3143，表示 IPv6 通配监听。如果客户端明确请求 127.0.0.1，需要检查云服务器的 GatewayPorts。本次未提供该设置的实际输出，GatewayPorts yes 是可能原因。

GatewayPorts行为
no强制仅本机访问，默认值
yes强制通配地址监听
clientspecified允许客户端选择监听地址

本次保留现有监听方式，没有修改服务端设置。通配监听的实际外部可达性取决于云安全组、主机防火墙和网络路由。后续若需核对，可在云服务器执行以下命令，并检查相关 Match 块。

sudo sshd -T | grep '^gatewayports'
sudo grep -RnE '^[[:space:]]*(GatewayPorts|Match|Include)' \
    /etc/ssh/sshd_config /etc/ssh/sshd_config.d/
