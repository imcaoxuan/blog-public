使用 systemd-resolved 为 WireGuard 配置按域名分流的 DNS

通过 wg-quick 的 PostUp 和 systemd-resolved 路由域，让指定域名使用 WireGuard 内网 DNS，其他域名使用公共 DNS。

WireGuard に接続した後は、内部ドメインだけをトンネル内の DNS でクエリし、それ以外のドメインは引き続き公共 DNS を使用したい場合があります。すでに systemd-resolved を使用している Linux システムでは、DNS ルーティングドメインを直接設定し、wg-quick の PostUp によって自動適用できます。DNS 転送サービスを追加でインストールする必要はありません。

目標と適用環境#

本文では次の例を使用します。

項目設定
WireGuard インターフェースwg0
トンネル内 DNS172.30.0.1
デフォルト DNS223.5.5.5
内部 DNS を介してクエリするドメインhome.arpa、example.com、example.net およびそれらのサブドメイン

example.com と example.net はサンプルドメインなので、必要に応じて置き換えるか削除してください。ここで設定するのはドメインのサフィックスです。トップレベルドメインに限定せず、corp.example.com のようなサブドメインも指定できます。

wg-quick が WireGuard を管理し、systemd-resolved がシステムの DNS を管理する Armbian、Debian、Ubuntu に適用できます。NetworkManager などのツールが直接管理する WireGuard 接続では、これらのフックが実行されるとは限りません。対応する管理ツールの設定方法を使用してください。

まず実際の環境を確認します。

resolvectl --version
wg --version
systemctl is-active systemd-resolved
resolvectl status
ls -l /etc/resolv.conf
cat /etc/resolv.conf

/etc/resolv.conf に次の内容が含まれている場合、通常、プログラムがローカルスタブ経由で systemd-resolved にアクセスしています。

nameserver 127.0.0.53
options edns0 trust-ad
search .

このファイルはそのまま残してください。2 つの上流 DNS サーバーに変更しないでください。nameserver が複数あるだけでは、域名ごとの分岐を表現できません。本文では既存の DNS ルーティング機能を使用します。システムに resolvectl がない、またはサービスが一停止している場合は、先に本機の DNS 管理方法を確認してください。

1. デフォルト DNS の設定#

設定ディレクトリを作成してファイルを編集します。

sudo mkdir -p /etc/systemd/resolved.conf.d
sudo vim /etc/systemd/resolved.conf.d/90-split-dns.conf

次を書き込みます。

[Resolve]
DNS=
DNS=223.5.5.5
FallbackDNS=
Domains=
Domains=~.

空の DNS= と Domains= は、それまでに蓄積されたグローバルな一覧を消去し、その後、本文で必要な値を設定します。FallbackDNS= はフォールバックの一覧を消去します。これはドメインごとの分岐ルールではありません。

~. はすべてのドメインに一致するルーティングドメインです。後で wg0 により具体的なドメインサフィックスを設定すると、それらのサフィックスが優先して一致します。

sudo systemctl restart systemd-resolved

この手順で変更するのはグローバル設定であり、他のネットワークインターフェース上の DNS ルーティングドメインは消去されません。他のインターフェースですでに ~.、または同じかより具体的なドメインルールが設定されている場合は、先にそのインターフェースを所有するネットワーク管理設定で競合を解消してください。

2. WireGuard に DNS フックを追加する#

既存の設定を編集します。

sudo vim /etc/wireguard/wg0.conf

既存の [Interface] セクション内に次を追加します。

PostUp = resolvectl dns %i 172.30.0.1
PostUp = resolvectl domain %i '~home.arpa' '~example.com' '~example.net'
PostUp = resolvectl default-route %i no

既存のアドレス、キー、Peer およびルーティング設定は保持してください。もともと DNS = ... がある場合は、その項目を削除してください。これにより、wg-quick が resolvconf 経由でもう一組の DNS を設定するのを避けられます。重複する [Interface] セクションを新しく作成しないでください。

各行の作用は以下のとおりです。

設定作用
resolvectl dns %i 172.30.0.1このインターフェースの DNS サーバーを設定する
resolvectl domain %i ...このインターフェースが担当する DNS ルーティングドメインを設定する
resolvectl default-route %i no一致しないドメインのデフォルト DNS 経路としてこのインターフェースを使用しない

wg-quick は %i をインターフェース名に置き換えるため、例えば wg0 になります。複数の PostUp は設定された順に実行されます。

default-route no は DNS サーバーの選択にのみ影響し、IP のデフォルトルートは変更しません。また、明示的に設定された ~. ルーティングドメインを上書きすることもできません。この分割は、主にグローバルな ~. とインターフェース上の具体的なサフィックスによって実現されます。

DNS サーバーは、このトンネル経由で到達可能でなければなりません。Peer の AllowedIPs が 172.30.0.1 を対象に含むことを確認してください。たとえば 172.30.0.0/24 がすでに含まれていれば十分です。追加する必要がある場合は、適切なネットワークまたは 172.30.0.1/32 を追記し、既存のルートを上書きしないでください。DNS で名前を解決できても、そのサービスのアドレスへ到達できるとは限りません。対象ネットワークには引き続き適切なルートが必要です。

3. トンネルを切断せずにすぐ適用する#

wg0 がすでに実行中の場合は、ファイルを保存して次を実行します。

sudo resolvectl dns wg0 172.30.0.1
sudo resolvectl domain wg0 '~home.arpa' '~example.com' '~example.net'
sudo resolvectl default-route wg0 no
sudo resolvectl flush-caches

これらのコマンドは現在の実行時状態を更新します。設定ファイルの PostUp は、次回起動時に自動的に適用されます。wg syncconf だけでは PostUp は再実行されません。

インターフェースがまだ起動していない場合は、元々使用していた管理方法で起動します。

sudo systemctl start wg-quick@wg0

SaveConfig = true を使用している場合、インターフェースを停止すると、実行時の状態によって設定ファイルが上書きされる可能性があります。変更内容が失われないよう、変更前にこのオプションを適切に設定してください。

4. 分割を検証する#

実際の設定を確認します。

resolvectl status

グローバル設定に 223.5.5.5 と ~. が、wg0 に 172.30.0.1 と指定した 3 つのルーティングドメインが表示されるはずです。

以下の内部ドメインを、内部環境で実際に存在するレコードに置き換えてください。

resolvectl query nas.home.arpa
resolvectl query www.baidu.com

期待されるルールは以下のとおりです。以下の表は設定目標であり、実機でのテスト出力ではありません。

クエリDNS サーバー
home.arpa、nas.home.arpa172.30.0.1
example.com、git.example.com172.30.0.1
example.net、a.b.example.net172.30.0.1
www.baidu.com223.5.5.5

実際のパケット送信先を確認する場合は、1 つのターミナルで次を実行します。

sudo tcpdump -ni any 'port 53 and (host 172.30.0.1 or host 223.5.5.5)'

別のターミナルでキャッシュを消去してから、再度クエリします。直接 dig @172.30.0.1 ... を実行すると、その DNS が利用可能かしか確認できず、システムの分割ルールが有効になったことを証明できません。

ルーティングドメインの一致方法#

~home.arpa は、DNS の選択にのみ使用されるルーティングドメインです。home.arpa 自体とすべてのサブドメインに一致しますが、短い名前に対して自動的にサフィックスを補完することはありません。たとえば nas をクエリしても、自動的に nas.home.arpa になるわけではありません。

短い名前の補完が本当に必要な場合は、~ の付かない home.arpa を検索ドメインとして使用できます。検索ドメインも DNS ルーティングに参加します。本文では完全なドメイン名を使用し、统一して ~ を付けています。

systemd-resolved は、一致するラベル数が最大のドメインを優先します。そのため ~home.arpa は ~. より具体的です。同じ最良一致ドメインが複数のインターフェースにある場合、クエリが複数のインターフェースへ並行して送信されることがあります。設定が重複しているインターフェースを、単純な主系・予備系の関係として理解することはできません。

1 回のコマンドで複数のドメインをスペース区切りで指定します。

sudo resolvectl domain wg0 '~home.arpa' '~example.com' '~example.net'

このコマンドは、インターフェース原有的ドメイン一覧を置き換えるものであり、追記ではありません。ドメインを追加する場合は、同じコマンドですべてを指定し、PostUp も同時に変更してください。

使用上の制約とトラブルシューティング#

  • インターフェースを削除するとルールも消えます。 トンネル切断後、元々プライベートだったドメインがグローバル DNS によってクエリされる場合があります。この設定は、「トンネル切断時はプライベートドメインの外部送信を禁止する」ポリシーではありません。
  • DNS の分割とサービスのルーティングは別の問題です。 公共 DNS を 223.5.5.5 に設定しても、そのサーバーへの IP トラフィックが物理 NIC を通るとは限りません。フルトンネルやポリシールーティングの場合、WireGuard 経由で送信されることもあります。
  • アプリケーションはシステム DNS を迂回する場合があります。 ブラウザー内蔵の DoH、プロキシソフト独自の DNS 設定、または DNS を直接指定するプログラムは、これらのルールに従わないことがあります。
  • プロキシによるハイジャックで実際の経路が変わる可能性があります。 sing-box の TUN やファイアウォール規則が 53 番ポートを横取りする場合は、その規則とパケットキャプチャの結果を併せて確認してください。
  • ランタイム設定の再設定が必要な場合があります。 systemd-resolved だけを再起動した後や、他のネットワーク管理ツールがインターフェースの DNS を書き換えた後には、resolvectl status を確認し、必要なら 3 つのコマンドを再実行してください。

名前を解決できない場合は、まずルーティングとサービスの状態を確認します。

ip route get 172.30.0.1
resolvectl status wg0
journalctl -u systemd-resolved -n 50 --no-pager

併せて、トンネル接続先の DNS が待ち受けているアドレスと、ファイアウォールがクライアントからの UDP/TCP 53 クエリを許可していることを確認します。以前に別の DNS 転送方式を使用していた場合は、その競合する設定を先に削除してください。例として、ローカルマシンの別ポートを指すグローバル DNS などが該当します。

補足：Debian で WireGuard を使用しない場合の DNS 分割#

内部 DNS に Debian のネットワークインターフェース経由で直接到達できる場合は、そのインターフェースにルーティングドメインを設定します。以下では eno1 を例にします。

クエリドメイン上流 DNS
home.arpa およびそのサブドメイン192.168.99.123
その他のドメイン192.168.99.1

systemd-resolved をインストールして設定する#

まず ip route get 192.168.99.123 を実行し、出力の dev を確認します。以下の eno1 を実際のインターフェース名に置き換えてください。

Debian 12 または 13 で resolvectl: command not found と表示される場合は、systemd-resolved をインストールできます。このパッケージが /etc/resolv.conf を引き継ぐため、先に現在の設定をバックアップしてください。すでに systemd-resolved を使用している場合は、インストールを省略できます。Debian 12 パッケージ情報と Debian 13 パッケージ情報を参照してください。

sudo cp -L /etc/resolv.conf /etc/resolv.conf.before-resolved
sudo apt install systemd-resolved

/etc/systemd/resolved.conf.d/ を作成し、その中の 90-split-dns.conf に次を書き込みます。

[Resolve]
DNS=
DNS=192.168.99.1
Domains=
Domains=~.

グローバル設定を適用してから、現在のインターフェースの DNS ルーティングドメインを設定します。

sudo systemctl restart systemd-resolved
sudo resolvectl dns eno1 192.168.99.123
sudo resolvectl domain eno1 '~home.arpa'
sudo resolvectl default-route eno1 no

~home.arpa はグローバルな ~. より具体的であるため、優先して一致します。resolvectl status で、他のインターフェースにも同じまたはより具体的なルーティングドメインが設定されていないか、また eno1 に意図した内部 DNS のみが設定されているかを確認してください。

永続化して IPv6 を保持する#

上記の 3 つのインターフェースコマンドは、実行時状態を変更します。systemd-networkd を使用している場合、networkctl status eno1 で Network File を確認します。たとえばファイル名が 10-eno1.network なら、/etc/systemd/network/10-eno1.network.d/90-split-dns.conf に次を書き込みます。

[Network]
DNS=
DNS=192.168.99.123
Domains=
Domains=~home.arpa
DNSDefaultRoute=no

[DHCPv4]
UseDNS=no
UseDomains=no

[DHCPv6]
UseDNS=no
UseDomains=no

[IPv6AcceptRA]
UseDNS=no
UseDomains=no

sudo networkctl reload を実行し、その後 resolvectl status eno1 で有効になっていることを確認します。上記設定でフィルターされるのは、DHCP と IPv6 RA から供給される DNS サーバーとドメインだけです。IPv6 アドレスとルーティングは、引き続き既存の設定によって決まります。IPv4 アドレス上の DNS サーバーでも、IPv6 の AAAA レコードを返せます。systemd.network マニュアルを参照してください。

ifupdown を使用している場合、/etc/network/interfaces の既存の iface eno1 inet ... セクションに次を追加します。

    post-up resolvectl dns "$IFACE" 192.168.99.123
    post-up resolvectl domain "$IFACE" '~home.arpa'
    post-up resolvectl default-route "$IFACE" no

他のサービスが DHCP または RA で学習した DNS を systemd-resolved に登録している場合は、該当するサービスで自動 DNS を無効にするか設定を調整し、その後、実際に有効なインターフェースの DNS 一覧を確認してください。

検証#

nas.home.arpa を内部ネットワークに実際に存在するレコードに置き換えます。そのドメインに AAAA が設定されていない場合は、公開クエリで IPv6 レコードの解決を確認し、内部ネットワークの A レコードで分割を確認します。

resolvectl status
resolvectl query --type=A nas.home.arpa
resolvectl query --type=AAAA nas.home.arpa
resolvectl query --type=AAAA www.debian.org

送信先も確認する場合は、先に sudo resolvectl flush-caches を実行し、クエリと 동시에パケットをキャプチャします。

sudo tcpdump -ni any 'port 53 and (host 192.168.99.123 or host 192.168.99.1)'
