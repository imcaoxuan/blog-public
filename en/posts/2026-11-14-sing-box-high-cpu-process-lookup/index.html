Diagnosing sing-box High CPU at Low Traffic: Process Lookup Overhead

A Go pprof investigation identifying process ownership lookup as roughly 84% of sampled CPU time.

Findings and verification status#

The dominant CPU cost was connection ownership lookup, particularly buildProcessPaths. A process_name rule had just been added before the incident. That change is strongly consistent with the profile and is the leading trigger.

The hotspot is confirmed; a post-removal comparison has not yet been reported. This report does not claim that removing the rule has already restored normal operation, or that a specific release bug has been established.

Personal hostnames and account names are omitted. The original application name is replaced with example-cli.

Environment and symptoms#

  • N1 device running Linux ARM64.
  • sing-box 1.14.4.
  • Build environment: go1.26.10 linux/arm64, CGO enabled.
  • Revision: c005f35300ce76427dc285481ec5695f5b179cd2.
  • Low external traffic and quiet logs, but persistently high CPU.
  • perf was unavailable. The investigation used the built-in pprof endpoint and analyzed the profile on a Mac.

Initial top output:

PID    COMMAND   VIRT     RES     SHR    %CPU   %MEM  TIME+
20776  sing-box  1484040  130060  41288  355.4   7.1  139:35.45

Under the usual top CPU accounting mode, 355.4% represents about 3.55 CPU cores. RES is approximately 127 MiB. The roughly 1.42 GiB VIRT value is not physical memory consumption. TIME+ is accumulated CPU time.

Busy loops, GC pressure, and internal traffic loops were initial hypotheses, not established findings.

Collecting a CPU profile#

Confirm the build and service arguments#

Run on the Linux host:

sing-box version
systemctl show sing-box -p ExecStart --no-pager
command -v perf

command -v perf produced no output, and the attempted perf commands failed with command not found. No perf profile was collected. A root shell does not need sudo.

Enable the local pprof endpoint#

These examples assume the service loads /etc/sing-box/config.json. If it uses -C or other configuration arguments, use the same arguments for validation rather than checking one file in isolation.

Back up the configuration:

cp -a /etc/sing-box/config.json \
  "/etc/sing-box/config.json.bak.$(date +%Y%m%d-%H%M%S)"

Merge debug into the existing experimental object, preserving other fields. This fragment is not a complete configuration:

{
  "experimental": {
    "debug": {
      "listen": "127.0.0.1:6060"
    }
  }
}

Bind the diagnostic endpoint to loopback; do not expose it directly to the Internet. Validate before restarting:

sing-box check -c /etc/sing-box/config.json &&
systemctl restart sing-box

A restart briefly interrupts proxy connections and discards the current runtime state. If the symptom disappears, wait for it to recur before profiling.

A profile was successfully collected in this incident, demonstrating that this diagnostic path works in this build. The exact revision’s full source was not retrieved during the investigation; the testing branch references below are not a source-level guarantee for that revision.

Sample during high CPU#

curl --noproxy '*' -fsS http://127.0.0.1:6060/debug/pprof/

curl --noproxy '*' -fS --max-time 45 \
  -o /tmp/sing-box-cpu.pprof \
  'http://127.0.0.1:6060/debug/pprof/profile?seconds=30'

curl --noproxy '*' -fsS --max-time 15 \
  -o /tmp/sing-box-goroutines.txt \
  'http://127.0.0.1:6060/debug/pprof/goroutine?debug=2'

–noproxy ‘*’ prevents proxy environment variables from affecting these local requests. The goroutine dump is supplementary; the findings here rely on the CPU profile, not on unprovided goroutine contents.

Analyze on a computer with Go installed#

Copy the profile to a Mac or another computer with Go. Installing Go on the N1 is unnecessary.

go tool pprof -top /tmp/sing-box-cpu.pprof
go tool pprof -top -cum /tmp/sing-box-cpu.pprof

Reading the evidence#

The profile reports:

Duration: 30s
Total samples = 66.94s (223.12%)

Average CPU use during this window was approximately 223%. This does not contradict the earlier 355.4% top reading: they cover different time windows.

Function or pathCumulative samplesCumulative share
direct Inbound.NewPacketConnectionEx58.41s87.26%
Router.searchProcessInfo56.54s84.46%
process.FindProcessInfo56.33s84.15%
process.buildProcessPaths54.37s81.22%
syscall.Readlink30.39s45.40%
os.ReadDir13.83s20.66%
runtime.gcBgMarkWorker3.57s5.33%

The dominant path was:

direct inbound UDP connection handling
→ route matching
→ searchProcessInfo / FindProcessInfo
→ findProcessPath / buildProcessPaths
→ ReadDir, Readlink, and related system calls

flat measures samples in a function itself; cum includes its callees. These nested percentages overlap and must not be added together. Syscall6 accounted for 64.03% flat, but that alone does not identify the responsible feature. The cumulative view traces it back to process lookup.

GC was not the dominant cost. The profile also does not support blaming encryption or bulk forwarding as the main CPU consumer.

protocol/direct.(*Inbound) means the direct inbound, not selection of the direct outbound. If that inbound receives DNS, investigate that listener next. The function name alone does not establish DNS traffic or prove a traffic loop.

The triggering rule and the find_process misconception#

The recently added matching fragment was equivalent to:

{
  "process_name": ["example-cli"]
}

This is a matching fragment, not a complete rule example.

Determining whether a connection belongs to that application requires process ownership lookup. A connection that ultimately fails to match can still incur the lookup cost. Low traffic volume therefore does not imply low CPU cost. The profile alone does not establish whether lookup frequency, scan cost, or cache behavior changed.

find_process: false is not a global prohibition on process lookup. The official documentation describes this option as enabling additional process lookup for logging when no process_name, process_path, package_name, user, or user_id rules exist. Rules that need ownership information can still trigger lookup.

Additional limitations:

  • Process matching concerns processes on the proxy host; it cannot identify application processes running on another client device.
  • A Python CLI command name may differ from its reported process name. Verify the actual identity rather than assuming example-cli will match.
  • This incident does not establish that every process_name rule causes high CPU.

Minimal remediation and acceptance criteria#

Search the text configuration:

grep -RInE \
  '"(find_process|process_name|process_path|process_path_regex|package_name|user|user_id)"' \
  /etc/sing-box --include='*.json' --include='*.jsonc'

This does not expand binary rule sets and may include files the service does not load. Interpret results alongside the actual startup arguments.

Recommended procedure:

  1. Back up the current configuration.
  2. Remove the entire newly added process rule, restoring the previous rule state. Do not remove only the matching field while retaining an action: that could create an unconditional rule.
  3. If process matching is unnecessary, disable any additional find_process setting.
  4. Validate with the actual configuration arguments, then restart.
  5. Observe CPU under comparable client activity and traffic, and collect another 30-second profile.

Acceptance criteria:

  • CPU drops substantially and remains stable during observation.
  • Process lookup no longer dominates the new profile.
  • DNS and proxy routing still behave as intended.

A restart alone can temporarily suppress a symptom, so an immediate CPU drop is insufficient to fully verify the cause. If the hotspot persists, inspect other loaded process/user rules and the source of direct inbound UDP requests before changing unrelated TUN, GC, or QUIC settings.

If behavior regresses, restore the backup, validate, and restart. Restoring the process rule may also restore the high CPU condition. After diagnosis, remove the added debug configuration and restart to close the diagnostic endpoint.
