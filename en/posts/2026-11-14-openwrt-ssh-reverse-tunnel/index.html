Expose a Local Service to a Cloud Server with an OpenWrt SSH Reverse Tunnel

Forward a local service on port 3143 with SSH -R and manage startup and reconnection with procd.

Goal and environment#

A service already listens on 127.0.0.1:3143 on OpenWrt. The cloud server should reach it through its own 127.0.0.1:3143. OpenWrt initiates the SSH connection, which also works when the local network is behind NAT.

The environment is OpenWrt 23.05.2 x86_64 with an OpenSSH client and a cloud server running sshd. All usernames, hostnames, and key paths below are placeholders.

The reverse tunnel was confirmed working. The cloud server was subsequently observed listening on :::3143, and its existing server configuration was retained. The procd configuration below provides persistent operation. Reboot and network recovery still require the acceptance checks described here.

Install and test interactively#

Run on OpenWrt.

opkg update
opkg install openssh-client
/usr/bin/ssh -V

Prepare a key that supports unattended login. This example uses /etc/ssh/vps-3143_ed25519. Install its public key in the cloud account’s authorized_keys, and verify the server host key on the first connection. Reuse existing working keys and SSH Host configuration where applicable.

/usr/bin/ssh -NT \
    -i /etc/ssh/vps-3143_ed25519 \
    -o ExitOnForwardFailure=yes \
    -R 127.0.0.1:3143:127.0.0.1:3143 \
    tunnel@example.com

The first address pair in -R requests a listener on the cloud server. The second identifies the destination reached from OpenWrt. Keep the existing local service running. This command creates no additional local listener on port 3143. The requested cloud-side port must be available.

For a service on another LAN host, change the destination, for example to -R 127.0.0.1:3143:192.168.10.20:3143.

Test on the cloud server. The following command assumes an HTTP service. For HTTPS, use the appropriate hostname, protocol, and certificate configuration.

curl -v http://127.0.0.1:3143/

Run persistently with procd#

Create /etc/init.d/vps-tunnel-3143 on OpenWrt.

#!/bin/sh /etc/rc.common

START=95
USE_PROCD=1

start_service() {
    procd_open_instance
    procd_set_param command /usr/bin/ssh -NT \
        -i /etc/ssh/vps-3143_ed25519 \
        -o BatchMode=yes \
        -o ExitOnForwardFailure=yes \
        -o ConnectTimeout=10 \
        -o ServerAliveInterval=15 \
        -o ServerAliveCountMax=3 \
        -R 127.0.0.1:3143:127.0.0.1:3143 \
        tunnel@example.com
    procd_set_param respawn 3600 10 0
    procd_set_param stdout 1
    procd_set_param stderr 1
    procd_close_instance
}

SSH stays in the foreground so procd can supervise it. BatchMode=yes disables interactive prompts, so the service must have access to a usable authentication key. ConnectTimeout=10 bounds connection establishment. With a 15-second keepalive interval and three unanswered probes, SSH exits after approximately 45 seconds of unresponsiveness. respawn 3600 10 0 configures a 3600-second crash accounting window, a 10-second restart delay, and unlimited retries.

ExitOnForwardFailure=yes exits when the remote listener cannot be established. An unavailable destination service can coexist with a live SSH tunnel, so verify the application separately.

Stop the interactive tunnel first to release the cloud-side port, then enable the service.

chmod +x /etc/init.d/vps-tunnel-3143
/etc/init.d/vps-tunnel-3143 enable
/etc/init.d/vps-tunnel-3143 restart

Verification and maintenance#

Inspect service state and logs on OpenWrt.

ubus call service list '{"name":"vps-tunnel-3143"}'
logread -e vps-tunnel-3143

Inspect the listener and request the application on the cloud server.

sudo ss -lntp 'sport = :3143'
curl -v http://127.0.0.1:3143/

Acceptance checks include a successful application request, automatic recovery after an OpenWrt reboot, and reconnection after a temporary network outage. Existing TCP connections are interrupted during reconnection and must be recreated by the application.

After editing the script, run /etc/init.d/vps-tunnel-3143 restart. To stop it and disable startup, run the following.

/etc/init.d/vps-tunnel-3143 stop
/etc/init.d/vps-tunnel-3143 disable

Troubleshooting notes#

Could not request local forwarding#

The following error occurred during setup.

bind [127.0.0.1]:3143: Address in use
channel_setup_fwd_listener_tcpip: cannot listen to port: 3143
Could not request local forwarding.

This indicates a local forwarding request. Check the actual command for an extra -L and SSH configuration for LocalForward. The existing local service occupying port 3143 is expected.

Temporarily adding -F /dev/null excludes user and system SSH configuration. It also skips Host aliases, port settings, identity files, and ProxyJump settings. It is unnecessary for normal operation. The full original command and configuration were unavailable, so the source of the extra local forwarding request was not established.

The cloud server listens on :::3143#

The observed sshd listener was :::3143, an IPv6 wildcard address. When the client explicitly requests 127.0.0.1, inspect the server’s GatewayPorts setting. Its effective value was not supplied in this case. GatewayPorts yes is a possible explanation.

GatewayPortsBehavior
noForces local-only access, the default
yesForces wildcard binding
clientspecifiedAllows the client to select the listening address

The existing listener behavior was retained without changing the server configuration. External reachability depends on cloud security groups, host firewall rules, and routing. For later inspection, run these commands on the cloud server and review applicable Match blocks.

sudo sshd -T | grep '^gatewayports'
sudo grep -RnE '^[[:space:]]*(GatewayPorts|Match|Include)' \
    /etc/ssh/sshd_config /etc/ssh/sshd_config.d/
