使用 systemd-resolved 为 WireGuard 配置按域名分流的 DNS

通过 wg-quick 的 PostUp 和 systemd-resolved 路由域，让指定域名使用 WireGuard 内网 DNS，其他域名使用公共 DNS。

After connecting to WireGuard, you may sometimes want only internal domain names to be queried through the DNS in the tunnel while all other domain names continue to use public DNS. On Linux systems that already use systemd-resolved, you can configure DNS routing domains directly and then apply them automatically through wg-quick’s PostUp, without installing an additional DNS forwarding service.

Goals and Applicable Environment#

This article uses the following examples:

ItemConfiguration
WireGuard interfacewg0
Tunnel DNS172.30.0.1
Default DNS223.5.5.5
Domains queried through the internal DNShome.arpa, example.com, example.net, and their subdomains

example.com and example.net are example domains; replace or remove them as needed. The configuration here applies to domain suffixes and is not limited to top-level domains; it can also be a subdomain such as corp.example.com.

This applies to Armbian, Debian, or Ubuntu systems where WireGuard is managed by wg-quick and system DNS is managed by systemd-resolved. WireGuard connections managed directly by tools such as NetworkManager do not necessarily execute these hooks; use the configuration method for the corresponding management tool.

First check the actual environment:

resolvectl --version
wg --version
systemctl is-active systemd-resolved
resolvectl status
ls -l /etc/resolv.conf
cat /etc/resolv.conf

If /etc/resolv.conf contains the following, it usually means that programs access systemd-resolved through the local stub:

nameserver 127.0.0.53
options edns0 trust-ad
search .

Leave this file as it is; do not replace it with two upstream DNS servers. Multiple nameserver entries cannot themselves express per-domain split routing. This article uses systemd-resolved’s existing DNS routing capabilities. If the system lacks resolvectl or the service is not running, first determine how DNS is managed on the machine.

1. Set the Default DNS#

Create the configuration directory and edit the file:

sudo mkdir -p /etc/systemd/resolved.conf.d
sudo vim /etc/systemd/resolved.conf.d/90-split-dns.conf

Write the following:

[Resolve]
DNS=
DNS=223.5.5.5
FallbackDNS=
Domains=
Domains=~.

The empty DNS= and Domains= entries clear the previously accumulated global lists before the values required by this article are set. FallbackDNS= clears the fallback list; it is not a per-domain routing rule.

~. is a routing domain that matches all domain names. After more specific domain suffixes are later configured for wg0, those suffixes will take priority.

sudo systemctl restart systemd-resolved

This step changes the global settings and does not clear DNS routing domains on other network interfaces. If another interface already has ~. or an identical or more specific domain rule, resolve the conflict first in that interface’s network management configuration.

2. Add DNS Hooks to WireGuard#

Edit the existing configuration:

sudo vim /etc/wireguard/wg0.conf

Add the following within the existing [Interface] section:

PostUp = resolvectl dns %i 172.30.0.1
PostUp = resolvectl domain %i '~home.arpa' '~example.com' '~example.net'
PostUp = resolvectl default-route %i no

Retain the existing address, key, peer, and routing configuration. If there was already a DNS = ... entry, remove it so that wg-quick does not also configure a separate set of DNS servers through resolvconf. Do not create a duplicate [Interface] section.

The purpose of each line is as follows:

ConfigurationEffect
resolvectl dns %i 172.30.0.1Sets the DNS server for this interface
resolvectl domain %i ...Sets the DNS routing domains handled by this interface
resolvectl default-route %i noPrevents this interface from being used as the default DNS path for unmatched domains

wg-quick replaces %i with the interface name, such as wg0. Multiple PostUp commands run in configuration order.

default-route no affects only DNS server selection. It does not modify the IP default route and cannot override an explicitly configured ~. routing domain. This split routing is implemented primarily through the global ~. and the specific suffixes on the interface.

When wg-quick down runs normally, the interface is removed and the corresponding per-link DNS settings disappear as well. Therefore, there is no need to add PostDown = resolvectl revert %i; in fact, running revert after the interface has been removed may result in the interface not being found.

The DNS server must be reachable through the tunnel. Make sure the peer’s AllowedIPs covers 172.30.0.1, for example if it already includes 172.30.0.0/24. If additional coverage is needed, append the appropriate subnet or 172.30.0.1/32; do not overwrite existing routes. The fact that DNS resolution works does not mean the service addresses are reachable; the business subnets still need the corresponding routes.

3. Apply Immediately Without Disconnecting the Tunnel#

If wg0 is already running, save the file and run:

sudo resolvectl dns wg0 172.30.0.1
sudo resolvectl domain wg0 '~home.arpa' '~example.com' '~example.net'
sudo resolvectl default-route wg0 no
sudo resolvectl flush-caches

These commands update the current runtime state, while the PostUp entries in the configuration file automatically apply them the next time it starts. Running only wg syncconf does not re-run PostUp.

If the interface has not yet been started, start it using the original management method, for example:

sudo systemctl start wg-quick@wg0

If SaveConfig = true is used, note that it may overwrite the configuration file with the runtime state when the interface is shut down. Handle this option properly before making changes to avoid losing the file modifications.

4. Verify the Split Routing#

View the actual configuration:

resolvectl status

You should see 223.5.5.5 and ~. in the global settings, and 172.30.0.1 along with the three specified routing domains under wg0.

Replace the following internal domain name with a record that actually exists:

resolvectl query nas.home.arpa
resolvectl query www.baidu.com

The expected rules are shown below. These are the configuration goals, not output from a test on an actual machine:

QueryDNS server
home.arpa, nas.home.arpa172.30.0.1
example.com, git.example.com172.30.0.1
example.net, a.b.example.net172.30.0.1
www.baidu.com223.5.5.5

To confirm where packets are actually sent, run the following in one terminal:

sudo tcpdump -ni any 'port 53 and (host 172.30.0.1 or host 223.5.5.5)'

Clear the cache and query again in another terminal. Running dig @172.30.0.1 ... directly only verifies that the DNS is available; it does not prove that the system’s routing rules are in effect.

How Routing Domains Match#

~home.arpa is a routing domain used only for DNS selection: it matches home.arpa itself and all of its subdomains, but it does not automatically append a suffix to short names. For example, a query for nas will not automatically be turned into nas.home.arpa.

If short-name completion is genuinely required, you can use the search domain home.arpa without ~; search domains also participate in DNS routing. This article uses fully qualified domain names and consistently uses ~.

systemd-resolved gives priority to the domain with the greatest number of matching labels. Therefore, ~home.arpa is more specific than ~.. If multiple interfaces have the same best-matching domain, queries may be sent in parallel to multiple interfaces; interfaces with duplicated configuration should not be understood as a simple primary/standby relationship.

Pass multiple domains in a single command, separated by spaces:

sudo resolvectl domain wg0 '~home.arpa' '~example.com' '~example.net'

This command replaces the interface’s existing domain list rather than appending to it. When adding domains, include the full list in the same command and update PostUp at the same time.

Usage Boundaries and Troubleshooting#

  • Rules disappear when the interface is removed. After the tunnel is disconnected, private domain names may instead be resolved by the global DNS. This setup is not a policy for preventing private domain names from being sent externally when the tunnel is disconnected.
  • DNS split routing and service routing are separate concerns. Setting the public DNS to 223.5.5.5 does not guarantee that IP traffic destined for it will go through the physical network interface; a full tunnel or policy routing may still route it through WireGuard.
  • Applications may bypass system DNS. A browser’s built-in DoH, a proxy application’s independent DNS configuration, or a program that directly specifies a DNS server may not follow these rules.
  • Proxy hijacking may still alter the actual path. If sing-box TUN or firewall rules intercept port 53, inspect them together with the packet-capture results.
  • Runtime configuration may need to be reapplied. After restarting systemd-resolved on its own, or after another network management tool rewrites the interface’s DNS settings, check resolvectl status and rerun the three commands if necessary.

If resolution fails, first check the routing and service status:

ip route get 172.30.0.1
resolvectl status wg0
journalctl -u systemd-resolved -n 50 --no-pager

Also confirm the tunnel peer’s DNS listening address and that the firewall permits UDP/TCP port 53 queries from clients. If you previously used an additional DNS forwarding solution, first remove its conflicting configuration, such as a global DNS entry pointing to another port on the local machine.

Reference Documentation#

  • systemd-resolved: query routing rules
  • resolved.conf: global DNS and routing domains
  • resolvectl: interface DNS, domain, and default-route
  • Official WireGuard wg-quick manual

Software versions and default network managers vary between distributions. When deploying, you can use the local man resolvectl, man resolved.conf, and man wg-quick to verify the configuration.

Supplement: DNS Split Routing on Debian Without WireGuard#

When the internal DNS can be accessed directly through a Debian network interface, set the routing domain on that interface. The following uses eno1 as an example.

Query domainUpstream DNS
home.arpa and its subdomains192.168.99.123
Other domains192.168.99.1

Installing and Configuring systemd-resolved#

First, use ip route get 192.168.99.123 to inspect the dev in the output, then replace eno1 below with the actual interface name.

If Debian 12 or 13 reports resolvectl: command not found, you can install systemd-resolved. The package will take over /etc/resolv.conf, so back up the current configuration first. Skip the installation if systemd-resolved is already in use. See Debian 12 package description and Debian 13 package description.

sudo cp -L /etc/resolv.conf /etc/resolv.conf.before-resolved
sudo apt install systemd-resolved

Create /etc/systemd/resolved.conf.d/ and write the following to 90-split-dns.conf within it:

[Resolve]
DNS=
DNS=192.168.99.1
Domains=
Domains=~.

Apply the global configuration, then set the DNS routing domain for the current interface:

sudo systemctl restart systemd-resolved
sudo resolvectl dns eno1 192.168.99.123
sudo resolvectl domain eno1 '~home.arpa'
sudo resolvectl default-route eno1 no

~home.arpa is more specific than the global ~., so it takes priority. Use resolvectl status to check whether other interfaces are also configured with the same or more specific routing domains, and whether eno1 has only the intended internal DNS.

Persisting the Configuration and Preserving IPv6#

The three interface commands above modify the runtime state. If systemd-networkd is used, use networkctl status eno1 to view the Network File. For example, if the file is named 10-eno1.network, write the following to /etc/systemd/network/10-eno1.network.d/90-split-dns.conf:

[Network]
DNS=
DNS=192.168.99.123
Domains=
Domains=~home.arpa
DNSDefaultRoute=no

[DHCPv4]
UseDNS=no
UseDomains=no

[DHCPv6]
UseDNS=no
UseDomains=no

[IPv6AcceptRA]
UseDNS=no
UseDomains=no

Run sudo networkctl reload, then use resolvectl status eno1 to confirm that it took effect. The settings above only filter DNS servers and domains supplied by DHCP and IPv6 RA; IPv6 addresses and routes are still determined by the existing configuration. A DNS server on an IPv4 address can also return IPv6 AAAA records. See the systemd.network manual.

If ifupdown is used, add the following to the existing iface eno1 inet ... stanza in /etc/network/interfaces:

    post-up resolvectl dns "$IFACE" 192.168.99.123
    post-up resolvectl domain "$IFACE" '~home.arpa'
    post-up resolvectl default-route "$IFACE" no

If other services also register DNS learned through DHCP or RA with systemd-resolved, disable automatic DNS or adjust its configuration in the corresponding service, then check the actual effective interface DNS list.

Verification#

Replace nas.home.arpa with a record that actually exists on the internal network. If the domain does not have an AAAA record configured, use a public lookup to verify IPv6 record resolution, and verify the split routing through an internal A record.

resolvectl status
resolvectl query --type=A nas.home.arpa
resolvectl query --type=AAAA nas.home.arpa
resolvectl query --type=AAAA www.debian.org

If you also need to confirm the packet destination, first execute sudo resolvectl flush-caches, then perform the queries while capturing packets:

sudo tcpdump -ni any 'port 53 and (host 192.168.99.123 or host 192.168.99.1)'
