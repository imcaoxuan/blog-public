On a Debian server with relatively little memory, I originally used CrowdSec to analyze SSH and web logs, then used Firewall Bouncer to synchronize ban decisions to nftables.

This setup could dynamically block IP addresses based on observed attack behavior. However, for a server with only a few hundred MiB of memory that runs several personal services, its resource overhead needed to be reconsidered. I ultimately adopted the following combination:

  • Website: Caddy + GeoIP country allowlist + manual IP allowlist.
  • SSH: Fail2ban reads the systemd journal and blocks anomalous sources through nftables.

This article documents the complete migration process, as well as the log-source and startup-ordering issues encountered during deployment. All domain names, addresses, and host identifiers have been replaced with examples. Commands are run as the root user.

I. First, Clarify the Changes in Protection Capabilities#

ItemPrevious SetupNew Setup
Web access controlCrowdSec analyzed logs and generated ban decisionsCaddy allows requests based on the source country or IP address
Anomalous SSH loginsCrowdSec SSH scenarioFail2ban SSH jail
Web behavior detectionDepends on the installed Collections and ScenariosNot retained in this article
Community threat intelligenceCould use CrowdSec community feedsNot integrated in this article
Where web requests are rejectedFirewall Bouncer firewall rulesCaddy HTTP request-processing stage

A country allowlist cannot serve as an equivalent substitute for behavior detection. Malicious requests from allowed countries may still reach the application, and Caddy’s GeoIP rules will not cover other public ports that do not pass through it.

II. When Checking Memory Usage, Check RSS and Swap Together#

First, get an overall picture:

free -h

systemctl show crowdsec crowdsec-firewall-bouncer \
    -p Id -p MemoryCurrent

ps -eo pid,comm,rss,args --sort=-rss | head -n 15

Looking at RSS alone may underestimate a process’s memory usage because some anonymous memory has already been swapped out. You can sort by the combined RSS and Swap usage:

for status_file in /proc/[0-9]*/status; do
    awk '
        /^Name:/   { name=$2 }
        /^VmRSS:/  { rss=$2 }
        /^VmSwap:/ { swap=$2 }
        END {
            if (rss+swap > 0)
                printf "%12d %12d %12d %s\n", rss+swap, rss, swap, name
        }
    ' "$status_file" 2>/dev/null
done | sort -nr | head -n 5

The four columns are, in order: Total KiB, RSS KiB, Swap KiB, and process name. This is a process ranking; if the same service has multiple processes, they need to be aggregated further.

During this investigation, CrowdSec’s RSS was approximately 42 MiB and VmSwap was approximately 225 MiB, for a rough total of 267 MiB. This shows that it was indeed a component worth slimming down, but the entire 267 MiB should not be treated as physical memory.

You also need to distinguish between “Swap is already being used” and “frequent paging is currently occurring”:

vmstat 1 10

Observe the samples after the first row. si and so indicate the per-second swap-in and swap-out amounts, respectively. A high Swap usage level does not by itself mean that continuous paging is currently taking place.

For other high-usage processes, you can use the PID to identify the service:

systemctl status 实际PID --no-pager --full

After confirming its purpose, choose whether to disable it:

systemctl disable --now 实际服务名.service

III. Back Up and Disable CrowdSec#

It is recommended to save the configuration before starting. If circumstances permit, validate the new setup before disabling the old one to minimize the interval during which protection is being switched.

The following backup directory is intended for the first migration. Use a different directory for repeated operations to avoid overwriting the initial state.

install -d -m 0700 /root/security-migration-backup

cp -a /etc/crowdsec /root/security-migration-backup/
cp -a /etc/caddy /root/security-migration-backup/
cp -a /usr/bin/caddy /root/security-migration-backup/caddy.original

nft list ruleset > /root/security-migration-backup/nftables.before.nft

systemctl list-unit-files --no-pager 'crowdsec*' \
    > /root/security-migration-backup/crowdsec-units.before.txt

This assumes that the original Caddy binary is located at /usr/bin/caddy. If it is actually elsewhere, inspect the service definition first:

systemctl cat caddy

3.1 Disable Scheduled Jobs and Resident Services#

First, inspect the CrowdSec-related units:

systemctl list-unit-files --no-pager 'crowdsec*'

The following loop uses Bash to disable any CrowdSec timers it finds:

while read -r crowdsec_timer _; do
    if [ -n "$crowdsec_timer" ]; then
        systemctl disable --now "$crowdsec_timer"
    fi
done < <(
    systemctl list-unit-files \
        --type=timer --no-legend --no-pager 'crowdsec*'
)

Stop the Bouncer first, then the engine, and mask both units to prevent them from being started again:

systemctl disable --now crowdsec-firewall-bouncer.service
systemctl disable --now crowdsec.service

systemctl mask crowdsec.service crowdsec-firewall-bouncer.service

Check the results:

systemctl is-active crowdsec crowdsec-firewall-bouncer
systemctl is-enabled crowdsec crowdsec-firewall-bouncer

The expected results are inactive and masked, respectively. The SSH, Caddy, and Nginx Collections are all executed by the CrowdSec engine and do not need to be disabled individually.

3.2 Check for Firewall Leftovers#

nft list tables

The default configuration generally uses table ip crowdsec and table ip crowdsec6. If they still exist after CrowdSec has been disabled, first compare them with the actual configuration under /etc/crowdsec/bouncers/ and confirm that they are tables dedicated to the Bouncer before deleting them:

nft delete table ip crowdsec
nft delete table ip6 crowdsec6

Only run the command corresponding to a table that actually exists and has been confirmed to belong to CrowdSec. Do not run nft flush ruleset, and do not disable the nftables service.

If CrowdSec rules were previously added manually to /etc/nftables.conf or a file referenced by it, remove the corresponding persistent definitions as well.

Keep the packages and configuration temporarily to make rollback possible; disabling the services is already sufficient to release the resources they were consuming at runtime.

IV. Add the GeoIP Module to Caddy#

This article uses the third-party module porech/caddy-maxmind-geolocation. It matches the client’s source using a local MaxMind-compatible MMDB database.

4.1 Record the Existing Version and Plugins#

/usr/bin/caddy version
/usr/bin/caddy list-modules --packages --versions
systemctl cat caddy

Existing plugins for DNS, rate limiting, and other features must be retained as well. Do not directly replace the original file with a new binary that contains only the GeoIP module.

4.2 Add the Module to a Copy#

On a server with limited memory, you can use Caddy’s online build download feature to avoid running the Go compiler locally:

install -d -m 0755 /usr/local/lib/caddy

install -m 0755 \
    /usr/bin/caddy \
    /usr/local/lib/caddy/caddy

/usr/local/lib/caddy/caddy add-package \
    github.com/porech/caddy-maxmind-geolocation

add-package updates to the latest Caddy and rebuilds it with the already registered plugins as well as the new plugin, but it does not guarantee that the original core version will be preserved. At this point, only the copy has been modified; the running service and the original /usr/bin/caddy remain unchanged.

If the core and plugin versions must be fixed, build Caddy with xcaddy on another machine with sufficient resources while specifying the versions, then upload a binary matching the target operating system and architecture.

Inspect the new version, the plugin list, and compatibility with the existing configuration:

/usr/local/lib/caddy/caddy version
/usr/local/lib/caddy/caddy list-modules --packages --versions

/usr/local/lib/caddy/caddy validate \
    --config /etc/caddy/Caddyfile \
    --adapter caddyfile

If the existing plugins cannot be rebuilt, or validation of the original configuration fails, resolve the compatibility issues before switching the service over.

4.3 Install the Country Database#

Obtain the GeoLite2 Country MMDB database from the official MaxMind website. After downloading and extracting it, assume that the file is located at /tmp/GeoLite2-Country.mmdb:

install -d -o root -g caddy -m 0750 /var/lib/caddy/geoip

install -o root -g caddy -m 0640 \
    /tmp/GeoLite2-Country.mmdb \
    /var/lib/caddy/geoip/GeoLite2-Country.mmdb

runuser -u caddy -- test -r \
    /var/lib/caddy/geoip/GeoLite2-Country.mmdb

If the final command exits successfully, the Caddy user can read the database. This assumes that both the service’s user and group are caddy, which should match the actual unit definition.

For checking only the country or region, the Country database is sufficient. Xray’s geoip.dat is not an MMDB file that can be used directly by this plugin.

V. Centrally Configure the Country and Manual IP Allowlists#

5.1 Define a Common Snippet#

This module does not provide an option that can be placed in the Caddyfile’s global {} block and automatically applied to every site. Instead, you can maintain the configuration centrally in a snippet and import it into each site.

In /etc/caddy/Caddyfile, place it after the existing global options block and outside the site definitions:

(geo_whitelist) {
    @geo_denied {
        # 手动 IP 白名单：替换为实际需要放行的 IP 或 CIDR
        not client_ip 203.0.113.10 198.51.100.0/24 2001:db8::10

        # 地区白名单
        not {
            maxmind_geolocation {
                db_path /var/lib/caddy/geoip/GeoLite2-Country.mmdb
                allow_countries CN HK JP
            }
        }
    }
}

All the addresses above are documentation example addresses. Individual IPv4 and IPv6 addresses and CIDR ranges can all be used. If a manual allowlist is not needed, remove the not client_ip ... line.

These two not directives mean: a request matches the denial rule only if it is neither in the manual IP allowlist nor in an allowed country. Do not place the positive client_ip and GeoIP matches side by side, because that would make both conditions mandatory.

SourceResult
Address in the manual IP allowlistPasses GeoIP access control
Other addresses in CN, HK, or JPPasses GeoIP access control
Other addresses, or addresses whose region cannot be identifiedReturns 403

The allowlist only exempts requests from the geographic restriction. Existing authentication mechanisms such as mTLS and application login remain effective.

5.2 Import It into Each Site and Ensure Checks Occur Before Business Logic#

app.example.com {
    import geo_whitelist

    # 原有 tls、log 等站点级配置保留在这里

    route {
        respond @geo_denied "Forbidden" 403

        handle {
            # 原有请求处理逻辑放在这里
            reverse_proxy 127.0.0.1:8080
        }
    }
}

files.example.com {
    import geo_whitelist

    route {
        respond @geo_denied "Forbidden" 403

        handle {
            reverse_proxy 127.0.0.1:9090
        }
    }
}

The outer route executes in the order written, ensuring that the GeoIP check happens first. The inner handle preserves the normal ordering of the existing business directives. Any other existing handle, handle_path, reverse_proxy, or file_server business handling in the site should also be placed inside the protected inner block to prevent the check from being bypassed.

Merely placing a respond directive on the first line of a site does not guarantee that it will execute first, because Caddy reorders directives by default.

Every site that requires protection must import and use this check. A snippet is not a global firewall that automatically covers all sites.

5.3 Real Client IP Addresses#

This example applies to public clients connecting directly to Caddy. If there is a CDN or reverse proxy in front of Caddy, configure the appropriate trusted_proxies so that client_ip and the GeoIP module use the real client address.

Merely passing X-Forwarded-For in a header does not make it trustworthy, and no source should be trusted unconditionally. If an ordinary TCP relay has no mechanism for preserving the real source address, Caddy may see only the relay server’s IP address.

VI. Make systemd Use the Separate Caddy Binary#

Using a separate path and a drop-in can prevent subsequent APT updates to /usr/bin/caddy from overwriting the custom binary currently in use. You will also need to maintain updates for the custom binary yourself.

install -d -m 0755 /etc/systemd/system/caddy.service.d

vim /etc/systemd/system/caddy.service.d/90-geoip-binary.conf

Write the following:

[Service]
ExecStart=
ExecStart=/usr/local/lib/caddy/caddy run --environ --config /etc/caddy/Caddyfile

ExecReload=
ExecReload=/usr/local/lib/caddy/caddy reload --config /etc/caddy/Caddyfile --force

If the original service uses different arguments, configuration paths, or an adapter, adjust the startup command to match the actual configuration.

Validate the setup before switching over:

/usr/local/lib/caddy/caddy validate \
    --config /etc/caddy/Caddyfile \
    --adapter caddyfile

After validation succeeds, run:

systemctl daemon-reload
systemctl restart caddy

systemctl status caddy --no-pager
journalctl -u caddy -n 50 --no-pager

The first switch to the new binary requires a restart, which briefly interrupts connections. When only modifying the configuration afterward, use:

systemctl reload caddy

Test with egress from different countries, or use a test server that is not included in the manual allowlist:

curl -I https://app.example.com/

Allowed sources should proceed to the backend, while other sources should receive a 403 response. Local and private-network addresses generally have no country attribution. If local monitoring is required, explicitly add the necessary IP addresses to the allowlist.

VII. Protect SSH with Fail2ban#

The Fail2ban version actually tested in this article is version 1.0.2 from the Debian 12 repository.

7.1 Install and Inspect#

apt update
apt install fail2ban python3-systemd nftables

fail2ban-client -V

/usr/sbin/sshd -T | grep '^port '
ss -lntp | grep sshd
journalctl -u ssh.service -n 20 --no-pager

The following configuration assumes that the SSH port is 22. You must change it if the actual port is different.

7.2 Create the SSH Jail#

vim /etc/fail2ban/jail.d/90-sshd.local

Write the following:

[sshd]
enabled = true

backend = systemd
journalmatch = _SYSTEMD_UNIT=ssh.service + _COMM=sshd
filter = sshd[mode=normal]

port = 22
protocol = tcp
banaction = nftables[type=multiport]

usedns = no
ignoreip = 127.0.0.1/8 ::1

findtime = 10m
maxretry = 5
bantime = 1h

If the same source accumulates five matching failure events within 10 minutes, its access to the SSH port will be blocked for one hour. The number of matching events does not necessarily equal the number of connections.

The + in journalmatch means OR between the two sets of conditions. When using the systemd backend, do not also configure a file-based logpath. If there is a fixed, trusted management egress address, you can add it to ignoreip as needed.

The .local file is used to override the configuration without modifying the .conf files supplied by the package.

7.3 Validate and Start#

fail2ban-client -t

After validation succeeds:

systemctl enable fail2ban
systemctl restart fail2ban

Wait a few seconds, then inspect the status:

fail2ban-client ping
fail2ban-client status
fail2ban-client status sshd

The expected result of ping is pong, and the jail list should contain only the items that need to be enabled. If any other jails are enabled by old configuration, explicitly disable them in the corresponding .local files.

Keep the existing SSH session open, then open another terminal and verify that normal key-based login still works.

VIII. Two Common Startup Issues#

8.1 SSH Log File Not Found#

ERROR Failed during configuration: Have not found any log file for sshd jail

This usually means that the current jail is looking for file-based logs while the system is actually using the journal. First, use journalctl -u ssh.service to confirm that the logs exist, then configure backend = systemd, install python3-systemd, and restart.

8.2 Client Cannot Find the Socket#

ERROR Failed to access socket path: /var/run/fail2ban/fail2ban.sock.
Is fail2ban running?

This is a client connection failure, and this line alone does not mean that the service failed to start. During this deployment, the client initiated its check in the same second as startup, while the service did not report Server ready until the following second. A later check worked normally.

Troubleshooting commands:

fail2ban-client -t
systemctl status fail2ban --no-pager --full
journalctl -u fail2ban -b -n 80 --no-pager
tail -n 80 /var/log/fail2ban.log

There is no need to manually create the socket; it should be created by the service process.

If you see:

WARNING 'allowipv6' not defined in 'Definition'. Using default one: 'auto'

This is a warning that the default value auto is being used. This deployment did not fail to start because of it.

IX. Verifying Fail2ban’s Actual Blocking Effectiveness#

9.1 First Verify IPv4 and IPv6 Rule Generation#

Use the documentation-reserved addresses to test rule synchronization:

fail2ban-client set sshd banip 203.0.113.10
fail2ban-client set sshd banip 2001:db8::10

nft list table inet f2b-table

Check whether the addresses appear in the sets and whether the associated rules match the actual SSH port. The default nftables action may create rules only when the first ban occurs, so not seeing the table while no bans exist is not necessarily a fault.

After completing the test, unban the addresses:

fail2ban-client set sshd unbanip 203.0.113.10
fail2ban-client set sshd unbanip 2001:db8::10

This test verifies the execution path, but it cannot prove that both the log detection criteria and actual network blocking have been verified. Ban records may be restored after the service restarts and should be explicitly removed after testing.

9.2 Verify the Connection from Another Controlled Server#

On the target server, ban the actual public IP address of another controlled server:

fail2ban-client set sshd banip 测试服务器实际公网IPv4

Then, on the blocked server, establish a new connection:

nc -4 -vz -w 5 目标服务器实际公网IPv4 22

You can also observe the SSH handshake:

ssh -4 -vvv \
    -o ConnectTimeout=5 \
    -o ConnectionAttempts=1 \
    -p 22 testuser@目标服务器实际公网IPv4

Replace all Chinese placeholder content and port numbers in the examples. The default nftables action is reject, and the connection may immediately report a rejection; if it is changed to drop, it will typically appear as a timeout. If the connection reaches the SSH host-key prompt or authentication stage, it means that this new connection was not blocked by the ban.

If necessary, capture packets on the target server to confirm whether the request arrives:

tcpdump -ni any -nn \
    'host 测试服务器实际公网IPv4 and tcp port 22'

Seeing the SYN in tcpdump does not mean that the firewall has allowed the connection through.

After removing the ban, repeat the connection from the test server:

fail2ban-client set sshd unbanip 测试服务器实际公网IPv4

A connection failure while banned and a successful connection after unbanning constitute an intuitive comparative result. Use an explicit IPv4 address and -4 to prevent the connection from actually using IPv6 when only IPv4 is banned. Do not use the sole current management access source for a ban test.

X. Plugin Overhead and Database Maintenance#

According to the project source code examined, this GeoIP plugin opens the database Reader on the first match and reuses it thereafter. It performs local queries while executing the matcher, with no remote GeoIP API requests and no additional cache of IP lookup results.

The maxminddb-golang library it uses supports mmap on Linux. The mapped file still consumes physical memory, but the database file size cannot be directly treated as additional Go heap memory. A snippet is configuration reuse and does not guarantee that all sites share the same plugin instance; mapped pages from the same file may be shared by the operating system.

For a personal service, the additional overhead is expected to be small. However, no definitive QPS, query latency, or net memory increase for the plugin has been measured on this machine. Data frames after a long-lived connection such as WebSocket has been established will not cause this GeoIP check to be executed again for every packet.

Using only the Country database and disabling unnecessary global debug during normal operation can reduce unnecessary data volume and per-request debug logs.

View Caddy’s actual total memory usage:

systemctl show caddy -p MemoryCurrent

caddy_pid=$(systemctl show caddy -p MainPID --value)

awk '/^(Rss|Pss|Swap|SwapPss):/' \
    "/proc/$caddy_pid/smaps_rollup"

The database requires ongoing maintenance. When updating it, first write a new file to the same directory, then replace the original through a rename operation, avoiding direct truncation of the original file while it is being used via mmap:

install -o root -g caddy -m 0640 \
    /tmp/GeoLite2-Country.mmdb \
    /var/lib/caddy/geoip/GeoLite2-Country.mmdb.new

mv -f \
    /var/lib/caddy/geoip/GeoLite2-Country.mmdb.new \
    /var/lib/caddy/geoip/GeoLite2-Country.mmdb

systemctl reload caddy

The reload here relies on --force in the earlier drop-in to ensure that Caddy reloads even when the configuration text has not changed. The plugin itself does not automatically download the database.

XI. Acceptance and Rollback#

During acceptance, confirm that:

  • CrowdSec and Firewall Bouncer have been stopped, and the related timers have been disabled.
  • The new binary that Caddy is actually running contains GeoIP and the original plugins.
  • Allowed regions and manually allowlisted IPs can pass, while other sources receive 403.
  • Fail2ban’s SSH jail has started processing new journal logs.
  • IPv4 and IPv6 rule generation and the ban/unban comparison test using a real connection have passed.
  • Normal SSH key-based logins and existing application access have not been unintentionally affected.

Check service status and total memory usage:

systemctl is-active caddy fail2ban
systemctl is-active crowdsec crowdsec-firewall-bouncer

free -h

To roll back to the original setup:

systemctl disable --now fail2ban

cp -a /root/security-migration-backup/caddy/. /etc/caddy/

rm /etc/systemd/system/caddy.service.d/90-geoip-binary.conf

systemctl daemon-reload
systemctl restart caddy

systemctl unmask crowdsec.service crowdsec-firewall-bouncer.service
systemctl enable --now crowdsec.service
systemctl enable --now crowdsec-firewall-bouncer.service

This procedure preserves the original /usr/bin/caddy and the CrowdSec configuration. If any timers were previously enabled, restore the corresponding units according to their backed-up unit states. Once the Bouncer starts, it will resynchronize the decisions, so there is no need to blindly overwrite the entire old firewall snapshot.
